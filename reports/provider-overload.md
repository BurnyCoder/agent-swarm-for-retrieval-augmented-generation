# Service interruption and recovery protocol · November 19, 2026

The initial held-out run received its first unresolved capacity rejection at about 15:40 UTC. The API returned HTTP 503 or a failed Responses stream with the code `server_is_overloaded`. The requests span multiple methods. We suspended paid dispatch, retained committed answers and continued indexing public repository snapshots locally. The provider describes this code as temporary model-capacity exhaustion and recommends backoff. [OpenAI error codes](https://developers.openai.com/api/docs/guides/error-codes)

## Accounting

The original broker reserves the highest possible cost of the full context and maximum permitted output before every generation. Some failed calls had no usage object. For each stale reservation, the recovery tool submits the original model inputs and response schema to the provider's free input-token counting endpoint. Immutable previous-response IDs are included. A missing or uncountable input retains the original reserve. For a certified input we retain its entire token count at the maximum long-context input rate, plus **every permitted output token** at the maximum output rate. This is an upper bound even if a failed call consumed all permitted output. No unknown bill is recorded as zero. The original reservation, payload digest, exact provider token count, and revised bound are archived. A later authoritative charge can settle that reservation. Three initial checks covering chained Arctic, Codex and one-shot requests reproduced the input-token counts of their completed responses. The project key could not access organization-level billing. [OpenAI token counter](https://developers.openai.com/api/docs/guides/token-counting) · [Counting is free](https://help.openai.com/en/articles/4936856-understanding-and-counting-tokens) · [Luna rates](https://developers.openai.com/api/docs/models/gpt-6-luna)

The per-answer export sums distinct grader units in the ledger. A technical repeat and its grader both run under the retry allocation. Before running technical repeats, a regression test reproduced a double count of that grader in the export and verified the correction. The ledger itself recorded one charge.

## Acquisition and analysis

This amendment was written after the interruption, before recovery inference. A supervisor watches provider errors independently of the model and answer scorer. The first explicit overload stops new dispatches. After a short drain window, it terminates the interrupted process and preserves atomic answer records. A small metered capacity check uses the retry allocation. It honors a supplied retry delay and otherwise uses exponential backoff. Question concurrency ramps through small batches after recovery. Within-question agent counts, evidence tools, reasoning effort, deadlines and resource ceilings come from the [original frozen revision](https://github.com/BurnyCoder/agent-swarm-for-retrieval-augmented-generation/releases/tag/v0.1.0-freeze).

The primary analysis retains original first-attempt scores, including recorded generation failures. A secondary analysis permits one technical repeat for each completed generation failure whose trace contains an explicit upstream overload. Eligibility depends only on the failure record and provider event. The retry-allocation limit applies across attempts, grading and capacity checks. The companion table compares three matched sets for each workload: first attempts, questions without any eligible failure, and questions in which every eligible failure has a successfully graded technical repeat.
